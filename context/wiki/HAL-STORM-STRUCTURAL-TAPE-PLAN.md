# HAL-Storm — Structural Tape / Mini-Refal

## Цель

Создать структурный индекс (Tape) над вложенными данными **без построения объектного AST**. Один механизм навигации и сопоставления должен работать с JSON в RAM, файлами на диске и, позднее, с YAML, Protobuf и Avro. Долгосрочная цель — **Mini-Refal + Markov** над Tape; JSONPath — удобный язык навигации.

## Сценарии

1. Большой JSON в RAM: повторные запросы к одной структуре.
2. JSON на диске, Tape в RAM.
3. JSON и Tape на диске: страничный доступ и кеширование.
4. Расширение на другие форматы. Для Protobuf и Avro отдельно учитывать наличие схемы; без схемы полная структурная интерпретация не гарантируется.

## Первая модель (v0)

```ocaml
type atom_role = Key | Value

type tag =
  | OpenObject | CloseObject
  | OpenArray  | CloseArray
  | Atom of atom_role
```

Логическая запись Tape: `[tag | source_offset | length | link]`.

- `source_offset` — абсолютное байтовое смещение в исходном документе, **не указатель на Cstruct**.
- `length` — длина исходного диапазона записи.
- `link` — индекс парной скобки для Open/Close; у Atom отсутствует.
- `Key` — имя поля объекта; `Value` — скаляр JSON. Вложенные объекты и массивы представлены структурными тегами.
- Tape **не владеет** исходными байтами; их время жизни и доступность обеспечивает источник данных.

Пример: `{"a": [1, 2]}`

| i | tag | offset | length | link |
|---|---|---:|---:|---:|
| 0 | OpenObject | 0 | 1 | 6 |
| 1 | Atom Key | 1 | 3 | — |
| 2 | OpenArray | 6 | 1 | 5 |
| 3 | Atom Value | 7 | 1 | — |
| 4 | Atom Value | 10 | 1 | — |
| 5 | CloseArray | 11 | 1 | 2 |
| 6 | CloseObject | 12 | 1 | 0 |

## Инварианты

1. Для скобок: `link(link(i)) = i`; типы пар совпадают.
2. В объекте: чередование `Key → значение`; значение — Atom Value, объект или массив.
3. В массиве: только значения, без Key.
4. Смещения абсолютные, диапазоны полуоткрытые `[offset, offset + length)`.
5. Результат не зависит от разбиения входа на чанки (для будущего потокового сканера).
6. `jump` даёт O(1) **на готовой Tape**, но не отменяет чтения байтов при её построении.

## План реализации

### Этап 1 — JSON → Tape в памяти (делаем сейчас)

- Согласовать тип записи и контейнер (пока можно обычный растущий массив; оптимизация позже).
- Написать однопроходный сканер JSON с явным стеком открытых контейнеров и backpatching `link` при закрытии.
- Учесть строки, escape-последовательности, числа, литералы, пробелы, разделители и ошибки синтаксиса. Не декодировать значения без необходимости.
- Тесты: пример выше, вложенность, пустые контейнеры, escaped quotes, неверные скобки, неполный JSON; проверка инвариантов.

**Критерий готовности:** корректная Tape для целого JSON-документа в памяти, без AST.

### Этап 2 — Streaming

- Сохранение состояния сканера между `Cstruct`-окнами Eio.
- Абсолютные смещения; отсутствие ссылок на переиспользуемый буфер.
- Тест эквивалентности: цельный документ = произвольные чанки, включая по одному байту.

### Этап 3 — Cursor / JSONPath

- `skip` через `link`; `SeekKey`, `SeekIndex`.
- Первый запрос: `$.users[1].name`.
- Определить политику получения исходных диапазонов для RAM и Disk.

### Этап 4 — Mini-Refal / Markov

- Определить символ, структурные скобки и семантику `s.` / `e.` переменных над Tape.
- Сопоставление по диапазонам без копирования; затем правила переписывания.
- Отдельно определить семантику изменений, чтобы не инвалидировать смещения исходного файла.

### Позже

- Дисковая Tape, страничная адресация/кеш, YAML-адаптер, Protobuf/Avro с учётом схем, компиляция DSL в специализированный автомат.

## Разделение работы

**Локальный Женя:** реализует только этап 1, тесты и короткую заметку о найденных ограничениях; не добавляет Eio, DSL, Refal или дисковый backend.

**Мы:** проверяем модель и инварианты по тестовой Tape, затем решаем, что действительно нужно для потокового режима и Mini-Refal.

**Принцип:** MaxEnt / Occam — не строим универсальный фреймворк заранее. Сначала доказуемая минимальная машина.
