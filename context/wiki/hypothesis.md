## 4. Гипотеза для проверки: HAL-Storm как конструктор специализированных потоковых автоматов

> **Статус:** исследовательская гипотеза. Не считается принятым архитектурным решением до экспериментальной проверки.

HAL-Storm может развиваться не только как HTTP/DRPC-сервер, а как движок построения **специализированных потоковых автоматов**.

Исходной сущностью системы в такой модели является не HTTP-запрос и не middleware pipeline, а **поток байт или событий**. Автомат может начинать работу непосредственно поверх сырого TCP-потока, ещё до появления какого-либо HTTP-уровня.

```text
TCP byte stream
      ↓
stream automaton
      ↓
recognised slices / events
      ↓
rewrite / transform rules
      ↓
application-specific state
```

HTTP в такой модели является лишь одним из возможных языков потока и удобным первым полигоном. Поверх TCP тем же способом могут обрабатываться:

- JSON;
- YAML;
- собственные текстовые протоколы;
- бинарные протоколы;
- DRPC;
- произвольные специализированные протоколы приложений.

Ключевая идея состоит в том, что HAL-Storm не обязан строить классический parser, который сначала целиком материализует документ, сообщение или AST.

Поток может постепенно распознаваться и преобразовываться в Refal-подобном стиле:

```text
последовательность
      ↓
образец / состояние
      ↓
распознавание
      ↓
slice / token / event
      ↓
преобразование
```

Для JSON это может выглядеть так:

```text
bytes
  ↓
structural symbols / spans
  ↓
tokens
  ↓
object / array events
```

Для бинарного протокола:

```text
bytes
  ↓
frame header
  ↓
length / type
  ↓
payload slice
  ↓
message event
```

При этом желательно сохранять основной принцип HAL-Storm:

> **не переносить данные без необходимости; перемещать состояния, границы, offsets и правила.**

### Композиция автоматов

На этапе описания системы могут существовать несколько малых автоматов:

```text
A → B → C
    └→ D
```

Однако эта композиция не обязана сохраняться как динамический runtime-граф.

Рабочая гипотеза состоит в том, что известные заранее:

- stream primitives;
- правила протокола;
- routing;
- policy;
- операции приложения;

могут быть специализированы и собраны в один конечный автомат приложения.

```text
stream primitives
+ protocol rules
+ routing / policy
+ application operations
        ↓
 specialise / compile
        ↓
Application Automaton
        ↓
native execution
```

Таким образом, универсальность HAL-Storm должна находиться не в одном универсальном сервере, конфигурируемом под множество приложений, а в:

- наборе примитивов потоковых автоматов;
- правилах их композиции;
- механизме специализации;
- механизме сборки конечной машины;
- средствах формальной и property-based проверки.

Конечный runtime при этом должен оставаться **конкретным и специализированным** под определённый протокол или приложение.

### HTTP как первый эксперимент

Текущий HTTP-парсер следует рассматривать прежде всего как удобный экспериментальный стенд.

HTTP намеренно не рассматривается как конечная архитектурная цель HAL-Storm.

Он полезен потому, что заставляет решить реальные задачи:

- частичный ввод;
- границы TCP-чтения;
- framing;
- переходы состояний;
- offsets;
- CRLF;
- заголовки;
- завершение header section;
- переход к body;
- ошибки;
- асинхронный transport.

После проверки базовой механики HTTP может быть заменён или дополнен более дешёвыми специализированными протоколами, включая собственный бинарный framing поверх TCP.

### Проверка гипотезы

Гипотеза должна подтверждаться экспериментально.

1. Текущий HTTP-автомат можно разложить на несколько простых потоковых primitives без потери детерминизма и контроля памяти.
2. Из этих primitives можно автоматически или полуавтоматически собрать автомат, эквивалентный написанному вручную.
3. Состояние автомата корректно переносится через частичные TCP-буферы и произвольные границы чтения.
4. Разметка потока может сохраняться в форме `offset + length` / slices без обязательного копирования исходных данных.
5. Тот же подход работает как минимум для одного не-HTTP формата — желательно простого бинарного протокола или JSON.
6. Композиция автоматов не требует обязательного runtime-слоя из объектов, callbacks, promises или heap-allocated pipeline.
7. Полученный автомат можно проверять через PBT и model checking.
8. По возможности структура автомата должна быть пригодна для дальнейшей специализации в компактный нативный код.
