## Замысел

Я начинаю с минимального protobuf wire format, чтобы понять, как бинарный протокол ложится на потоковый автомат HAL-Storm.

Я не хочу собирать сообщение целиком, хранить сетевые фрагменты или строить универсальный AST. Между окнами должны переноситься только состояние декодера, промежуточное значение и уже распознанные поля.

Целевая форма:

```text
window + protobuf_state + result_state
→ remaining_window + next_protobuf_state + next_result_state
```

Состояния первого черновика:

```text
Tag | VarInt | Payload
```

Минимальный пример — `08 01`:

```text
field_number = 1
wire_type = 0
value = 1
remaining = empty
```

После чтения key я хочу отделять номер поля от wire type, выбирать специализированный декодер и складывать результат непосредственно в известную структуру DRPC.

## Текущий статус

В `test/test_protobuf.ml` создан первый черновик: разбор младших битов key, рекурсивный проход varint, перенос `intermediate_value` и возврат непрочитанного хвоста `Cstruct`.

Это исследовательский набросок, а не готовый декодер и пока не проверяющий тест.

## Замечания к следующему шагу

- continuation bit varint проверяется как `byte land 0x80 <> 0`; результат маски равен `0` или `0x80`, но не `1`;
- protobuf key сам является varint, поэтому `field_number = key lsr 3` вычисляется после сборки key;
- при переходе через границу окна должны сохраняться accumulated value и shift;
- protobuf-сообщение само по себе не задаёт границу TCP-сообщения, поэтому внешний framing DRPC нужно определить отдельно;
- первый настоящий тест должен разобрать `08 01` и утверждением проверить поле, wire type, значение и пустой остаток.

## Архитектурный инвариант

Сетевое окно временно. Смысл прочитанного префикса хранится в состоянии автомата; сырые окна после обработки не сохраняются.

### `kshakirov` — 2026-09-25T09:30:02Z

#### Checkpoint: length-delimited и следующая задача

Я добавил первый черновой путь для protobuf wire type `2`.

Текущая схема:

```text
key
→ field_number + wire_type
→ varint length
→ Cstruct slice payload
→ decoded field + remaining window
```

`parse_delim_length` проверяет наличие заявленного количества байтов, возвращает `SliceVal` как представление payload без копирования и оставляет непрочитанный хвост окна для следующего поля. Сборка и прежний varint-тест проходят.

Новый путь wire type `2` ещё нужно закрепить отдельным тестом, например:

```text
0A 03 61 62 63
→ field 1
→ length 3
→ payload "abc"
→ empty remainder
```

#### Следующая задача: явное состояние продолжения

Я ввожу состояние protobuf-распознавателя, потому что без него нельзя корректно продолжать вычисление через границы сетевых окон и отличать незавершённый ввод от ошибки.

Минимальная смысловая форма:

```text
Tag
VarInt(field_number, accumulated_value, shift)
Payload(field_number, expected_length, consumed_length)
```

Результат обработки одного окна:

```text
Done(fields, remaining_window)
Continue(next_state, fields)
Malformed(error)
```

Состояние должно позволить продолжить:

- key, оборванный между окнами;
- многобайтовый varint;
- length varint;
- length-delimited payload, пришедший несколькими частями.

Оно же должно сделать явными ошибки: недопустимый wire type, переполнение или слишком длинный varint, недопустимый номер поля, превышение лимита payload и настоящий EOF внутри незавершённого элемента.

#### Владение payload

`SliceVal` является видом на исходный `Cstruct`. Для постоянного тестового буфера это корректно, но сетевой read buffer переиспользуется. Поэтому slice нельзя сохранять после следующего чтения без отдельного решения о времени жизни. Части payload должны либо потребляться немедленно следующим слоем, либо переноситься в явно принадлежащую результату память.

Архитектурный инвариант сохраняется: между окнами переносится смысл вычисления, а не сырые транспортные фрагменты.
