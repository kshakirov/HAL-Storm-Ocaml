## Goal

Build the first real vertical execution path from an accepted TCP connection down to the existing Wirth streaming automaton.

The server currently accepts clients, but parsing still lives separately from the transport path. This issue connects the layers without expanding HTTP semantics yet.

## Target vertical structure

```text
Eio server
  ↓
client handler
  ↓
requestParser
  ↓
Wirth parser
```

## Комментарии

### `kshakirov` — 2026-09-04T10:14:16Z

#### Buf_read integration checkpoint

The current vertical path has been tested with `Eio.Buf_read` and is working.

Current flow:

```text
Eio server
  ↓
client handler
  ↓
Eio.Buf_read
  ↓
requestParser
  ↓
Wirth parser
```

The implementation is intentionally being committed in this working state before changing the transport mechanism.

#### What was learned

`Eio.Buf_read` is useful as a high-level buffered reader, but it owns significant parts of the buffering policy internally:

- it reads from the underlying `flow` on demand;
- it maintains its own internal buffer;
- actual transport read boundaries are hidden from the parser;
- `max_size` limits the internal buffer size, but does not define the size of individual socket reads.

This is convenient for ordinary protocol parsing, but it removes control over a parameter that is important for the HAL-Storm experiment: **how the incoming byte stream is partitioned into chunks.**

#### Decision

Keep and commit the current working `Buf_read` implementation as a verified intermediate checkpoint.

The next step will replace `Buf_read` at the transport boundary with explicitly controlled reads from the Eio flow, most likely using `Eio.Flow.single_read`.

Target direction:

```text
TCP flow
  ↓
controlled read (N bytes maximum)
  ↓
chunk
  ├──→ request storage
  └──→ requestParser
          ↓
      Wirth parser
```

This will allow HAL-Storm itself to control transport chunk size and experimentally verify parser invariance under different stream partitions, for example `N = 1`, `N = 8`, `N = 64`, `N = 4096`. The parser result should not depend on this partitioning.

#### Consequence

`Eio.Buf_read` is not considered wrong or defective. It is being removed from this layer because its abstraction hides behavior that HAL-Storm deliberately wants to expose, control, and study. The current implementation remains a useful working baseline for comparison with the explicit-read version.

### `kshakirov` — 2026-09-08T15:39:07Z

#### Checkpoint: переход к чистому потоковому распознавателю

Вертикальный путь уже доведён до рабочего эксперимента на `Eio.Flow.single_read`: сервер выполнил много явных чтений для запроса с URI, содержащим 10 000 байтов, прошёл цикл обработки окон и завершил разбор состоянием `Finished`.

Этот результат пока подтверждает работу транспортного цикла, но следующий тест должен проверить не только факт многократного чтения, а сохранение смысла запроса через все границы окон.

#### Что хотим наблюдать

Диагностический результат интеграционного теста должен содержать:

```text
state=Finished
reads=N
bytes_read=M
parser_index=K
uri_length=L
```

Для запроса

```text
/api/v1/users/123/orders?big= + 10000 × A
```

ожидается:

```text
reads > 1
uri_length = 10029
```

- `reads > 1` подтверждает реальную фрагментацию входа;
- `bytes_read` считается как сумма фактических результатов `single_read`, а не размеров выделенных буферов;
- глобальный `parser_index` подтверждает, что автомат не начинал каждое окно заново;
- `uri_length = 10029` подтверждает, что offsets корректно пережили все границы окон.

Одного успешного ответа curl или общего числа прочитанных байтов недостаточно: транспорт может прочитать всё, даже если состояние распознавателя между окнами потеряно.

#### Архитектурная цель

Парсер Вирта должен стать чистым потоковым распознавателем. В памяти между чтениями остаются только:

- состояние автомата;
- абсолютная позиция и необходимые offsets/длины;
- распознанные свойства протокола: метод, framing, `Content-Length`, режим `chunked`, оставшаяся длина тела и другие необходимые метаданные.

Сырые фрагменты запроса не накапливаются и не склеиваются. Один рабочий `Cstruct` используется как текущее конечное окно; данные тела при необходимости передаются следующему потребителю потоково.

Целевая схема:

```text
TCP flow
  ↓ single_read
reusable Cstruct window + actual_read_length
  ↓
pure Wirth recognizer(window, parser_state)
  ↓
Finished | Malformed | Continue(next_parser_state)
```

#### Инварианты следующего шага

1. Автомат обрабатывает только `Cstruct.sub buffer 0 read_bytes`; хвост выделенного буфера не является входом.
2. Каждый прочитанный байт потребляется ровно один раз.
3. Конец окна означает продолжение, а не EOF и не синтаксическую ошибку.
4. `parserState` полностью описывает уже распознанный префикс и передаётся следующему чтению.
5. Ни request line, ни заголовки, ни тело целиком не материализуются без необходимости.
6. Результат распознавания не зависит от разбиения потока на окна.

Следующий сеанс: вернуть из слоя распознавания обновлённый `parserState`, учитывать фактический результат `single_read`, затем вывести перечисленные диагностические величины в ответе и проверить длинный URI.

### `kshakirov` — 2026-09-11T12:02:14Z

#### Checkpoint: явный потоковый контур замкнут

Исправлена передача объектов между итерациями клиентского цикла.

Текущая схема:

```text
single_read(flow, read_buffer)
  ↓ read_bytes
window = Cstruct.sub read_buffer 0 read_bytes
  ↓
wirth_parser(window, parser_state)
  ↓
new_parser_state
  ↓ NeedsMoreData
повторное single_read в исходный read_buffer
```

Роли теперь разделены явно:

- `read_buffer` — постоянная переиспользуемая область памяти одного соединения;
- `window` — временный вид только на фактически прочитанные байты;
- `parser_state` — продолжение вычисления между окнами.

В рекурсивный вызов снова передаётся исходный `read_buffer`, а не укороченный `window`. Поэтому короткое чтение больше не уменьшает ёмкость всех последующих чтений. Обновлённый `parserState` также сохраняется и передаётся следующей итерации.

Сборка и тесты проходят.

#### Точка остановки HTTP

HTTP-эксперимент остаётся рабочим, но незавершённым. При следующем возвращении к нему нужно проверить длинный URI через наблюдаемые величины:

```text
state=Finished
reads=N
bytes_read=M
parser_index=K
uri_length=10029
```

Также остаются EOF, строгая HTTP-валидация, `Content-Length`, `chunked` и потоковая передача тела.

#### Следующее направление

Основной фокус временно переключается на DRPC. HTTP будет использоваться как контрольный полигон и дорабатываться отдельными инкрементами. Для DRPC первым объектом исследования должен стать минимальный framing сообщения; накопление и склейка сырых фрагментов по-прежнему не допускаются без необходимости.
