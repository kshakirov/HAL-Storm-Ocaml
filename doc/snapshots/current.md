# Снимок состояния HAL-Storm

Дата анализа: 2026-08-25
Ветка: `dev`
Commit: `ff6452e` (`wirth 11`)

## Резюме

HAL-Storm уже не является пустым каркасом:

- Eio-сервер слушает TCP-порт `8081`;
- реализован черновой побайтовый автомат HTTP-запроса;
- парсер возвращает границы элементов через список смещений;
- существует демонстрационный разбор request line и заголовков;
- добавлена формальная модель автомата для `nuXmv`;
- проект собирается на OCaml 5.5.0;
- `dune runtest` завершается успешно;
- спецификация `nuXmv` формально истинна.

При этом проект пока является исследовательским прототипом автомата, а не действующим HTTP-сервером.

## Сильная сторона конструкции

В `lib/parser.ml` уже выражен правильный центральный замысел:

```text
байт + текущее состояние -> новое состояние + смещения
```

Это ясная конструктивная модель побайтового автомата:

- нет предварительного разбиения запроса на строки;
- исходная строка не копируется самим автоматом;
- переходы локальны и обозримы;
- хвостовая рекурсия подходит для линейного прохода;
- смещения позволяют позднее представить токены как окна исходного буфера.

Разделение ответственности также разумно: ДКА размечает поток, будущие преобразования токенов выполняются отдельно, Eio отвечает за транспорт.

## Проблемы автомата

### 1. Парсер может молча остановиться

В обработке метода переход для обычного байта действует при `index < 9`, а ошибка — при `index > 9`. Для байта с индексом ровно `9` не подходит ни одна из этих ветвей. Срабатывает общий переход:

```ocaml
| _ -> s
```

Парсер возвращает незавершённое состояние вместо `Error`. Ветка `index > 9` фактически недостижима.

Автомат смешивает три различных результата:

- успешное завершение;
- синтаксическую ошибку;
- отсутствие подходящего перехода.

### 2. Конец буфера выражен исключением

`Eio.Buf_read.any_char` выбрасывает исключение, когда данные закончились. Неполный запрос не превращается в явный результат вроде `NeedMoreData` или `Error`.

Для сетевого парсера требуется различать:

```text
Success | Malformed | Need_more_input
```

### 3. HTTP-синтаксис почти не проверяется

Автомат находит разделители, но пока не проверяет:

- допустимый HTTP-метод;
- URI;
- версию `HTTP/1.0` или `HTTP/1.1`;
- символы имени заголовка;
- правильность CRLF;
- ограничения длины URI и заголовков.

Это пока разметчик границ, а не валидирующий HTTP-парсер.

### 4. `check_method_3` логически неверен

`String.capitalize_ascii "GET"` возвращает `"Get"`, однако результат сравнивается с `"get"` и `"put"`. Функция возвращает `false` для этих методов. Строка короче трёх символов также приведёт к исключению. Сейчас функция не используется.

### 5. Zero-allocation пока остаётся целью

При переходах создаются новые записи `parserState`, а при обнаружении границ — новые элементы списка `offsets`:

```ocaml
{ state = ...; offsets = ...; index = ... }
cons ... offsets
```

Для исследовательского прототипа это нормально, но отсутствие аллокаций ещё не установлено. Сначала требуется доказать корректность, затем проводить измерения и оптимизацию.

## Состояние тестов

`test/test_parser.ml` является демонстрацией, а не проверяющим тестом:

- отсутствуют утверждения;
- результат только печатается;
- состояние `Success` не проверяется;
- смещения не сравниваются с ожидаемыми значениями;
- ошибочные и неполные запросы не исследуются.

Успешный `dune runtest` означает только то, что программа не упала на одном happy path.

Минимальный следующий набор проверок:

1. Обычный GET с заголовками.
2. Запрос без заголовков.
3. Неполный request line.
4. Отсутствующий `\n` после `\r`.
5. Слишком длинный метод.
6. Заголовок без двоеточия.
7. Несколько последовательных запросов в одном буфере.

## Формальная модель

`doc/automaton_1.smv` успешно проверяется в `nuXmv 2.2.0`, однако пока не моделирует реализацию достоверно.

Для действия `byteSeq` нет переходов, сохраняющих состояния `reqMethod`, `reqUri`, `reqVersion`, `headerName` и `headerValue`. Поэтому обычный байт попадает в общий переход:

```smv
TRUE : error;
```

Есть и прямое расхождение с реализацией:

- в OCaml `HeaderName + carriage -> Success`;
- в модели такого перехода нет.

Проверяемое LTL-свойство слабое. Поскольку большая часть путей быстро попадает в поглощающее состояние `error`, истинность свойства пока не подтверждает корректность парсера.

## Транспорт

`bin/main.ml` поднимает accept loop, но обработчик клиента:

- создаёт `Buf_read`;
- выводит число уже буферизованных байтов;
- не вызывает `wirth_parser`;
- не формирует HTTP-ответ;
- завершает работу, после чего соединение закрывается.

Транспортный каркас начат, но сервер пока не обрабатывает запросы.

## Инфраструктурные расхождения

- Локальный пакет `hal_storm` всё ещё pin'нут на `#master` и commit `740b910`, хотя рабочая ветка — `dev`.
- Прямой `dune build` собирает текущие файлы `dev`, но операции opam над пакетом могут использовать состояние старого pin.
- Текущие исходники не проходят `ocamlformat --check`.
- README считает операцию «Гребёнка» полностью невыполненной, хотя её прототип уже существует.
- Раздел текущего состояния в `AGENTS.md` устарел.
- Метаданные `dune-project` остаются шаблонными.
- `_build/` и `_opam/` не исключены посредством `.gitignore`.

## Проверенные факты

На момент снимка выполнены:

```text
opam exec --switch=. -- dune build @all
opam exec --switch=. -- dune runtest --force
nuXmv doc/automaton_1.smv
opam exec --switch=. -- ocamlformat --check ...
```

Результаты:

- сборка успешна;
- демонстрационный тест завершается успешно;
- LTL-спецификация модели истинна;
- текущие OCaml-файлы требуют форматирования.

## Рекомендуемый следующий шаг

Сейчас не следует расширять сервер или оптимизировать аллокации. Момент истины находится в семантике автомата:

```text
определить точный тип результата парсера
-> сделать переходы полными
-> заменить печатающий пример утверждениями
-> синхронизировать модель nuXmv
```

Только после этого следует подключать парсер к Eio-транспорту. Иначе получится быстрый сервер вокруг автомата, корректность которого пока не определена.
