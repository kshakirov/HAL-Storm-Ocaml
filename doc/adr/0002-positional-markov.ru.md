# ADR-0002 — Позиционные правила Маркова для границ строк JSON

## Context

Парсеру Tape нужен диапазон строки в исходных байтах без построения декодированного объекта. Текущий алгоритм проходит позиции слева направо, в каждой проверяет правила по порядку списка и при обычном совпадении меняет общую память Cstruct. Отдельное однобайтовое правило обратного слеша делает старый признак терминальности по длине образца неоднозначным.

## Decision

- Правило остаётся парой Cstruct: образец и замена. Образец непустой, правила создаются вне цикла прохода.
- Идём слева направо, на каждой позиции выбираем первое совпавшее правило списка. После обычной замены снова проверяем правила на той же позиции; при отсутствии совпадения сдвигаемся на байт. Это наш позиционный вариант, а не утверждение эквивалентности классическому глобальному приоритету правил НАМ.
- У обычного правила замена непустая и равна образцу по числу байтов. Набор замен не должен приводить к бесконечному повтору в той же позиции.
- Пустая правая часть означает терминальное правило: сообщаем совпадение и выходим, не заменяя и не удаляя образец. Это заменяет проверку длины левой части. Пустота здесь служит признаком, а не операцией удаления.
- В текущем наборе строк JSON правила экранированной кавычки и пары обратных слешей идут раньше терминальной неэкранированной кавычки; терминальное правило последнее в списке. Входим после открывающей кавычки. Выходим по первой неэкранированной закрывающей, последующий вход не меняем.
- Позиции считаем в исходных байтах. Сейчас результат — позиция терминальной кавычки и вид на хвост начиная с неё. Преобразование в диапазон/число потреблённых байтов должно явно учитывать начальное смещение вызова и включение обеих кавычек.
- Одинокий обратный слеш на границе окна требует отдельного результата неполного ввода. Действие этого правила и представление продолжения пока открыты. Нельзя зациклить его тождественной заменой или считать обычным несовпадением.

## Rationale

Равные длины сохраняют смещения. Срезы Cstruct разделяют память: замену пишем с локального нуля найденного окна, абсолютную позицию повторно не прибавляем. Пустая правая часть позволяет отличить терминальное правило без третьего поля и сохранить обычные однобайтовые образцы.

## Consequences

Обычная замена, повторная проверка и позиция терминального совпадения уже есть в прототипе. Терминальность по пустой правой части, продолжение неполного образца, восстановление и интеграция с Tape ещё не реализованы. Тест утверждает успех и позицию 72; побайтовый результат замен, несколько закрывающих кавычек и эквивалентность окон ещё не проверены. Представления Cstruct всё ещё создаются; zero-overhead не измерен.

### Открытая развилка: владение и мутация

| Вариант | Плюс | Цена / что решить |
|---|---|---|
| Копировать строку/вход и менять копию | Оригинал неизменен, обратный проход не нужен | Память и копирование; не склеивать весь префикс заново на каждом чтении; определить лимиты и неполный ввод |
| Менять текущее окно и восстанавливать | Нет полной копии строки | Прямые и обратные записи; восстановление при успехе, паузе и ошибке до переиспользования буфера; владение и образцы через границы окон |

Выбор не сделан. Примеры обратимых двухбайтовых маркеров: `0x01 0x02` для экранированной кавычки, `0x01 0x01` для пары обратных слешей. В корректной JSON-строке таких сырых байтов нет; для повреждённого входа нужна явная политика коллизий. Тестовые AA/BB для безопасного восстановления не подходят. Восстановление ограничивается преобразованным диапазоном, не затрагивая последующий вход.

В обоих вариантах нужно распознавание через границы окон. Короткое окно — не настоящий EOF, накопление само по себе не определяет конец строки. Для байтов, на которые ссылается Tape, требуется политика времени жизни. Реализацию правила одиночного слеша этот ADR не утверждает.
